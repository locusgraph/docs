# Store an event

One call writes one memory.

```typescript
const result = await client.storeEvent({
  graph_id: "acme",
  event_kind: "fact",
  context_id: "person:alice",
  source: "user",
  payload: { data: "Alice joined Acme" },
});
```

## The request

| Field | Required | What it is |
| --- | --- | --- |
| `graph_id` | Yes | The graph to write into |
| `event_kind` | Yes | What sort of memory this is: [Event kinds](/locusgraph/remember/event-kinds) |
| `payload` | Yes | The memory itself. Any JSON |
| `context_id` | No | The primary context, as `type:slug` |
| `source` | No | Where it came from: [Sources](/locusgraph/remember/sources) |
| `extends` | No | Context ids this is a more specific detail of |
| `related_to` | No | Context ids this is laterally associated with |
| `reinforces` | No | Context ids whose memories this strengthens |
| `contradicts` | No | Context ids whose memories this supersedes |
| `timestamp` | No | Unix timestamp, as a string. Defaults to now |

### payload

Arbitrary JSON. The server imposes no structure, so this is valid:

```typescript
payload: { data: "Alice joined Acme" }
payload: { data: "use useMemo for object props", good_example: "…", bad_example: "…" }
payload: { data: { role: "engineer", started: "2026-03-01" } }
```

`{ data: … }` is the convention, and the one everything else assumes. Reach past it when a memory genuinely carries structure worth keeping.

### The four link fields

Each takes an **array of context ids**, not a single string:

```typescript
await client.storeEvent({
  graph_id: "acme",
  event_kind: "fact",
  context_id: "person:alice",
  extends: ["org:acme"],
  related_to: ["project:billing_ui"],
  payload: { data: "Alice joined Acme" },
});
```

<Callout tone="note" title="Top-level links win">
  Link fields at the top level take precedence over anything inferred from `payload.data`. Say it
  explicitly and you are not relying on inference.
</Callout>

## The response

```typescript
{
  locus_id: "L1a2b3c4…",       // the memory this write landed on
  status: "created",           // created · unchanged · replaced · filtered
  confidence: 0.7,             // how far the engine trusts it, 0 to 1
  context_id: "person:alice",  // the normalized context, when you sent one
}
```

### What `status` tells you

A context holds one memory, so a write to a context that already has one is not a second memory. `status` says which of the four things happened.

| `status` | What happened | `locus_id` |
| --- | --- | --- |
| `created` | The context held nothing | The new memory |
| `unchanged` | Byte-identical to what it held. A retry, not an edit | The memory that was there |
| `replaced` | Different text, and the write sent `replace: true` | The memory, now rewritten |
| `filtered` | The admission gate did not admit it | `null` |

Writing text a context does not already hold **without** `replace: true` is refused with a `409`. See [Replacing a memory](#replacing-a-memory).

### `status: "filtered"` is not an error

A filtered write **succeeded** as a request: the event is recorded, and no memory was built from it. That is what happens to the Noise kinds: `noise`, `debug`, `log`.

`locus_id` is `null`, because there is no memory to name. The event itself is still in the log and readable at `GET /v1/events/{graph_id}/rejected`, which is what makes filtering rather than rejecting worth doing.

<Callout tone="trap" title="Check `status`, not just the absence of a throw">
  If you store a `fact` and get `filtered`, something about that write is not what you expected. A
  call that does not throw has been accepted; it has not necessarily been made findable.
</Callout>

## Replacing a memory

Changing what a context says is a decision, not something that should happen because you reused an id. So it has to be asked for:

```typescript
await client.storeEvent({
  graph_id: "alice",
  event_kind: "fact",
  context_id: "preference:theme",
  replace: true,
  payload: { data: "switched to light mode for daytime work" },
});
```

Without `replace: true`, the same write is refused, and the refusal says what it would have written over:

```json
409 {
  "success": false,
  "error": {
    "code": "CONFLICT",
    "message": "preference:theme already holds a memory; send replace: true to write over it",
    "held": {
      "locus_id": "L1a2b3c4…",
      "text": "prefers dark mode",
      "source": "user",
      "confidence": 0.7
    }
  }
}
```

`held` is there so you can decide in one round trip. A memory sourced `policy` at `0.95` is usually not one an agent's guess should overwrite; writing to a context of its own is the better answer.

<Callout tone="note" title="Links you do not mention are kept">
  A field the write omits is left alone, so correcting a typo does not cost the memory its
  `reinforces` or `related_to`. Send `reinforces: []` to clear one deliberately.
</Callout>

### `context_id` comes back normalized

The context you get back is the one the server actually stored, which may differ from what you sent. Use the returned value if you are going to reference it.

## Writing more than one

Three at a time is still three calls. Use [batch or a transaction](/locusgraph/remember/batch) instead: up to 1000 per request.
